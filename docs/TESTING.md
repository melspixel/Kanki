# Test and closure plan

A green compilation is not closure. A rewrite milestone closes only when every applicable gate below has evidence attached to the release commit.

## Gate 0 — CI execution sanity

Before interpreting any red product check, the minimal `.github/workflows/actions-probe.yml` must execute its `Runner started` shell step on the candidate/account configuration.

A GitHub job that terminates with no step list is an infrastructure/account/repository execution failure and is not evidence about Kanki source. Fix Actions execution first; do not shotgun-edit product code in response to zero-step failures.

## Gate A — deterministic host tests

- review state-machine order;
- deck collapse model;
- reviewer packet/body classes;
- persistent `#qa` lifecycle;
- real checksum-pinned MathJax inline/display SVG across successive dynamic
  renders of the same `#qa`, with stale completion isolation;
- no deck-specific selectors;
- ordinary SVG/image preservation and no global SVG/image/font overrides;
- backend-controlled autoplay and ordered answer-side AV replay, with autoplay/replay booleans covered both ways;
- ES5 syntax check for Kindle JavaScript, including CSS and diagnostics runtimes;
- generic CSS-variable/calc/flex compatibility contract;
- renderer diagnostics contract: metrics contain no element text; raw capture is disabled by default and bounded when enabled;
- launcher/report shell syntax;
- package manifest validation;
- pinned/checksummed KindleHF toolchain policy (no floating `latest` build input).

## Gate B — Anki integration

Using a disposable collection generated by the pinned backend:

- open/close collection;
- deck tree and collapse persistence;
- queue counts;
- render question and answer;
- AV tag extraction;
- basic/cloze typed-answer preparation/comparison plus known-empty and unknown-field handling;
- answer Again/Hard/Good/Easy and verify revlog;
- bury card;
- controlled pinned-server normal-sync state propagation and full-sync decision handling;
- controlled media byte propagation, status and idle-abort handling;
- reopen collection after every write sequence.

The canonical host recipe runs this gate against a pinned Anki sync server on
loopback with disposable clients, scratch server state and synthetic
credentials, then scans retained evidence for credential leakage. This closes
the controlled protocol/lifecycle fixture only; live AnkiWeb and PW6 acceptance
remain Gate E work.

## Gate C — renderer parity corpus

Each fixture stores backend HTML/CSS and expected semantic measurements from desktop Anki and Kindle:

- plain basic card;
- CSS variables and representative `calc()` expressions;
- flex row and flex column;
- gap handling on the target old WebKit;
- embedded scripts;
- image sizing;
- replay SVG plus unrelated SVG illustration;
- long bilingual content;
- MathJax;
- cloze;
- typed-answer input/result;
- multiple card templates (`card1`, `card2`);
- representative original COCA and existing user decks without APKG modification.

For each candidate fixture, renderer evidence should include the backend render packet plus privacy-safe measured Kindle layout. Raw card HTML/CSS is only captured with explicit test consent/sentinel.

Passing means relative hierarchy, DOM order, overflow and controls match the fixture contract. It does not require identical fonts or antialiasing.

## Gate D — firmware/ABI/package

- cross-build ARMv7 hard-float with checksum-pinned KindleHF toolchain;
- record the resolved toolchain release and SHA-256 in build identity;
- compare GLIBC/GCC symbol requirements with audited rootfs;
- verify required standard and Lab126 symbols;
- run loader/self-test against a mounted official rootfs where possible;
- build `kanki-device`, `kanki-sync`, `kanki-diag`, `kanki-raise`, `kanki-audio`, `kanki-gst-play` and typed Anki backend;
- produce one reproducible self-identifying ZIP with the canonical package
  recipe, whether the executor is hosted or local;
- compare two clean canonical builds of the exact candidate byte-for-byte;
- bind sorted archive paths, permissions and timestamps to source-controlled
  inputs and record the source date epoch/archive hash;
- verify `MANIFEST.sha256` and refusal of mixed/partial components;
- verify package includes diagnostic/report runtime and does not include `extensions/ranki`, `collection.anki2` or user `config.ini`;
- package contains no Amazon firmware or proprietary library bytes.

## Gate E — real PW6 hardware

1. Backup collection and install from a clean `extensions/kanki` directory.
2. Confirm build identity and system fingerprint.
3. Confirm `render-debug/` and privacy-safe `metrics.log` are created automatically; missing diagnostics is a failure.
4. Open collapsed and expanded deck trees and confirm persistence.
5. Review the parity corpus, including original representative APKG decks without modifying them.
6. Confirm long-card scrolling and no persistent layout/CPU work when the page is idle.
7. Confirm semantic replay and card-authored audio over AirPods, including repeated replay.
8. Answer at least one card with each rating, bury one card and restart.
9. Sync, restart, and verify schedule/media integrity on desktop Anki.
10. Exercise explicit full-upload/full-download decision paths on a disposable/safely backed-up collection.
11. Exercise back/exit, duplicate launch, sleep/wake and USB connection.
12. Export the default diagnostic bundle and confirm it contains no credentials, database, raw note text or raw card captures.
13. If renderer source capture is required, enable `enable-render-capture`, confirm only the bounded first render set is written, inspect/share deliberately, then disable it.
14. Roll back to the previous release without touching `anki_data`.

## Handoff reproduction test

Before release, a maintainer who did not author the implementation must be able to start with `docs/RESUME.md`, identify the exact source/toolchain pins, reproduce the non-hardware gates, build the same package recipe and understand the PW6 test/rollback path without chat context or undocumented commands.

## Closure rule

No `1.0` tag, no merge to `main`, and no “finished” status until Gate E is signed off on the target device. CI may establish Gates A–D; hardware evidence closes Gate E. Issue #11 checkboxes mean verified evidence, not merely implemented source.
